Contexto y Análisis de Falla

// EL REQUERIMIENTO

Escalabilidad asíncrona sin bloqueos

El sistema de la fintech requería conciliar un volumen constante de 10,000 transacciones por minuto contra múltiples APIs bancarias de terceros. No era viable bloquear hilos de base de datos en transacciones síncronas que dependieran de tiempos de respuesta externos variables.

// ANÁLISIS DE FALLA

Deadlocks e ineficiencia por contención

La implementación inicial utilizaba transacciones ACID síncronas, bloqueando filas en PostgreSQL. Ante fallos o picos de latencia en las APIs de terceros, la latencia p99 aumentaba por encima de los 4,000ms, agotando rápidamente la piscina de conexiones de la base de datos y produciendo fallos generales en cascada.

Implementación Técnica y Control de Idempotencia

TransactionReconciler.ts TypeScript (Strict) 
01 import { Transaction, OutboxStore } from './db';
02 import { RedisClient } from './redis';
03 
04 export class TransactionReconciler {
05   constructor(private db: DBClient, private cache: RedisClient) {}
06 
07   async processWithOutbox(tx: Transaction): Promise<void> {
08     const idempotencyKey = `tx:idemp:${tx.id}`;
09     
10     // Lock temporal en caché para evitar condiciones de carrera inmediatas
11     const locked = await this.cache.set(idempotencyKey, 'pending', 'NX', 'EX', 10);
12     if (!locked) throw new Error('Duplicate transaction in-flight');
13 
14     await this.db.transaction(async (manager) => {
15       // Escribir en outbox para mantener consistencia eventual garantizada
16       await manager.save(new OutboxStore(tx));
17       await manager.updateTransactionStatus(tx.id, 'processed');
18     });
19   }
20 }

Decisiones de Diseño y Post-Mortem Técnico

Consistencia Eventual vs Latencia

Sacrificamos la consistencia inmediata a cambio de una alta disponibilidad extrema. El estado de conciliación se garantiza de manera eventual en menos de 2 segundos, reduciendo la latencia de respuesta al usuario a solo 12ms promedio.

Seguridad y Defensa OWASP

Implementamos validación criptográfica estricta en el payload utilizando firmas HMAC SHA-256. Esto evita falsificaciones de lotes y garantiza que el origen de las transacciones procesadas provenga exclusivamente de endpoints autorizados.

Retrospectiva Técnica

Si tuviera que refactorizar el sistema hoy, reemplazaría el polling actual de workers por un esquema de observabilidad con telemetría distribuida utilizando OpenTelemetry, mejorando el diagnóstico de cuellos de botella en APIs de terceros.
